# 03 — Architecture

Rule of thumb: boring, well-supported tools; as few moving parts as possible.

## Tech stack (proposed)

| Part | Choice | Why |
|---|---|---|
| Desktop shell | **Tauri 2** | Makes a real Windows app from a web-page UI. Much smaller and lighter than Electron. The backend part is written in Rust, but we'll keep Rust code minimal. |
| UI | **TypeScript + React** (or Svelte, see open questions) | Huge ecosystem; I (Claude) can work in it fluently; lots of Japanese-text libraries exist for it. |
| Database | **SQLite** (one file on your PC) | No server to run. Easy to back up: copy one file. |
| Scheduler | **FSRS** via the `ts-fsrs` library | Proven open-source algorithm (same family Anki uses). No need to invent our own. |
| Romaji → kana typing | **WanaKana** library | Standard tool for this; WaniKani-style answer input. |
| Sentence splitting (later) | **kuromoji.js** or **Sudachi** | Splits Japanese text (which has no spaces) into words. |
| AI | **Anthropic Claude API** first, behind a small interface so other providers can be added | One provider is enough to start. |

### How the parts fit

```
┌──────────────── Tauri app window ────────────────┐
│  UI (TypeScript/React)                            │
│   ├─ screens: Today, Lessons, Reviews, Lookup…    │
│   ├─ FSRS scheduling (ts-fsrs)                    │
│   └─ talks to ↓                                   │
│  Backend (Rust, kept thin)                        │
│   ├─ SQLite database (your progress + content)    │
│   └─ AI requests → your chosen AI helper          │
└───────────────────────────────────────────────────┘
```

AI requests go through the backend, to whichever AI helper you picked in Settings (see "AI integration"). AI is off until you pick one.

## Content sources and licenses

We can't ship WaniKani, Bunpro or Anki-deck content. These open datasets cover most needs:

| Data | Source | License (summary) |
|---|---|---|
| Kanji: meanings, readings, grade, frequency, JLPT (old levels) | **KANJIDIC2** (EDRDG) | CC BY-SA 4.0: free to use, must credit, and shared changes stay under the same license |
| Dictionary: words, readings, meanings | **JMdict** (EDRDG) | CC BY-SA 4.0 |
| Kanji components | **KRADFILE / RADKFILE** (EDRDG) | EDRDG license (similar terms) |
| Stroke order | **KanjiVG** | CC BY-SA 3.0 |
| Example sentences (Japanese + English) | **Tatoeba**, as the Tanaka Corpus with EDRDG's word index (`examples.utf`) | CC BY 2.0 FR (some sentences CC0) |
| JLPT word/kanji lists | Community lists (no official list exists since 2010) | Varies; check each before use. *Not used yet*: KANJIDIC's pre-2010 JLPT levels are enough for ordering. |

Verified 2026-10-20. How we actually get the data:

- KANJIDIC2, JMdict and KRADFILE/RADKFILE come as JSON from **jmdict-simplified** (CC BY-SA 4.0), which converts the EDRDG files every week.
- Word **frequency** comes from the original JMdict XML (`JMdict_e.gz` from EDRDG), because the JSON conversion drops the frequency tags.
- **EDRDG terms we must follow:** credit the sources on a separate *About/Sources screen* (not just the launch screen), and keep the data updated regularly. `pnpm content:build` always fetches the latest release, so re-running it now and then covers the second rule.

**Gaps we fill ourselves:**

- **Mnemonics:** none of the open sources have them. Plan: AI drafts them, you approve or rewrite them (see 02-features G).
- **Component names:** WaniKani's names are its own. We name components ourselves, starting from KANJIDIC/KRADFILE meanings.
- **Grammar explanations:** no good open grammar database exists. Grammar point *names* (e.g. 〜ている) aren't owned by anyone; explanations get written by us with AI help and reviewed.

Because CC BY-SA is "share-alike", the app needs an **About/credits screen** listing these sources. Keeping the app private and personal is fine either way.

Datasets are downloaded and converted into the app's database by an **import script**, run once (and re-run to update), not by hand.

## Data model

Two kinds of data, in **two separate database files**, so a dataset update can never wipe your progress:

1. **`content.db`: study content.** Generated by `pnpm content:build`, shipped with the app, read-only at runtime. Rebuilt from scratch every time. Full schema: [`scripts/content/schema.sql`](../scripts/content/schema.sql).
2. **`user.db`: your stuff.** Review history, scheduling, your mnemonics/notes, your synonyms, your settings. Lives in the app's data folder and is never regenerated. Backed up daily to `Documents\Koihongo\Backups` (SQLite's backup API, so a copy is consistent even mid-session).

The two files connect through **item keys**, text IDs that stay stable across data updates:

| Key | Example | Stable because |
|---|---|---|
| `component:<glyph>` | `component:化` | KRADFILE glyph |
| `kanji:<character>` | `kanji:森` | the character itself |
| `word:<JMdict id>` | `word:1362530` | JMdict entry numbers never change |

### content.db (built)

```
meta, sources       build date, dataset versions, licences/credits (feeds the About screen)
components          glyph, display, name, stroke_count          (245)
kanji               character, meanings, readings, grade, JLPT, frequency, stroke-order SVG
                    (2,974: jōyō + jinmeiyō)
kanji_components    kanji → component
words               id, written, reading, other_forms, senses, priority, usually_kana
                    (22,647 common words)
word_kanji          word → kanji
sentences           id, japanese, english, kanji_words, unlisted (84,824)
word_sentences      word → sentence, up to 20 per word (the app shows the 3 you can read best)
levels              level, region (N5…N1, approximate), position in region, kanji needed to clear   (267)
path                position, item_key, kind, track, level      (7,869 items)
path_requirements   item_key → requires_key   (an item unlocks when these are learned)
mnemonics           item_key, kind, text      (Koihongo's default mnemonics)
search              term, field, item_key, weight, rank
                    (dictionary index over every word and kanji, ~226k terms)
```

### Tracks

`content.path` has a `track` column. The **kana** track (positions 1–224, built from [`scripts/content/kana.ts`](../scripts/content/kana.ts)) and the **main** track (components → kanji → words) each have their own lesson window and daily limit, so kana and kanji can be learned in parallel. Kana item keys are `kana:<character>`; kana have one card (`reading`, answered in romaji).

### How the default path is built

Code: [`scripts/content/path.ts`](../scripts/content/path.ts), tested in `path.test.ts`.

1. Take the 2,136 jōyō kanji. Sort them by old JLPT level (easiest first), then frequency, then stroke count.
2. Before each kanji, insert any of its components not already placed. Components are their own quick items (WaniKani's model), so the component 木 "tree" comes before the kanji 木.
3. After each kanji, insert up to **3 words** that have just become readable, most frequent first. Extra readable words wait for later slots.
4. Words only qualify if they're common, normally written with kanji, use only jōyō kanji, and score 20 or better on frequency. Frequency penalises "newspaper-only" words, which are often jargon or fragments of longer words.

Result: 241 components, 2,136 kanji, 5,492 words. Settings (`WORDS_PER_KANJI`, `MAX_PATH_WORD_PRIORITY`) are at the top of `build.ts`; tune them after real use.

### user.db (built)

Lives in `%APPDATA%\com.xel.nihongo\user.db`. Schema and future changes: [`src/db/migrations.ts`](../src/db/migrations.ts). The app applies new migrations on start; `PRAGMA user_version` records which have run.

```
srs_cards    item_key, card_type (meaning|reading), FSRS state, due, started_at
review_log   every answer: rating, what you typed, when   (for tuning the scheduler later)
notes        item_key, kind (mnemonic_meaning|mnemonic_reading|note), text,
             author (you|ai|ai_edited), created_at        (every version kept; newest = current)
synonyms     item_key, text                               (extra meanings you accept)
```

Unlock state isn't stored; it's worked out from `srs_cards` + `content.path_requirements`.

### How the app reaches the databases

```
React screen → src/srs/progress.ts (all logic) → Db interface → Rust db_query / db_batch → SQLite
```

- Rust ([`src-tauri/src/db.rs`](../src-tauri/src/db.rs)) holds **one connection**: `user.db`, with `content.db` attached **read-only** as `content`. So one query can join your progress with content (`FROM srs_cards JOIN content.path …`), and content can't be changed by accident.
- Rust offers only two generic commands: `db_query` (read rows) and `db_batch` (several writes in one all-or-nothing transaction). All study logic stays in TypeScript.
- Tests run the same TypeScript logic against in-process SQLite ([`tests/nodeDb.ts`](../tests/nodeDb.ts)) using the real content schema, so no app window is needed.
- Trade-off: the UI can run any SQL. That's fine for a local single-user app, but **AI output must never be rendered as raw HTML**, since that could let injected script reach the database.

### Scheduling and unlocking

Code: [`src/srs/`](../src/srs/). Pacing numbers: [`src/srs/settings.ts`](../src/srs/settings.ts).

- **FSRS** (ts-fsrs) with **day-based intervals only**, no 10-minute steps, because the app is built for one session a day. Answers are right/wrong, so only two ratings: Good and Again.
- **Lesson → first review after 4 hours**, so the first review tests memory rather than what was just on screen.
- **Typical intervals:** correct → ~3 days → ~2 weeks → longer. Wrong → back in 1–2 days.
- **Passed** = every card of an item has FSRS stability ≥ 3 days, which takes about two correct reviews over three days. Passing unlocks whatever requires the item.
- **Lesson offer:** unlocked, unstarted items within the next 40 path positions, in path order.
- **Backlog throttle:** 10 new lessons per study day, shrinking linearly as due reviews grow, and zero at 100 due.
- **Review order:** lowest estimated recall chance first, so a short session does the most important reviews.
- **Study day** runs 4 am → 4 am.

## AI integration

### How a request works (mnemonic workshop example)

1. You click "Rework mnemonic" on 森 (forest).
2. The app builds a request containing: the kanji, its meanings and readings, its components and their names, your current mnemonic, and a short instruction ("help the learner make a vivid, memorable mnemonic; keep it short; use the component names").
3. The backend sends it to your AI helper and shows the reply in a chat panel.
4. You chat back and forth. When you like one, "Use this" saves it as a new `notes` version marked `ai` (or `ai_edited` if you tweak it).

### Choosing a helper (2026-10-23)

AI is **off by default**, for everyone: nothing is sent anywhere until you pick a helper in Settings → AI helper (`src/ui/AiSettingsCard.tsx`, saved as `ai.*` rows in user.db `settings`, see `src/ai/settings.ts`). While it's off, the Ask AI and Explain buttons are hidden. The choices:

- **Claude Code** (below): your own Claude login, no key.
- **Anthropic API** (`src-tauri/src/ai_api.rs`): `POST https://api.anthropic.com/v1/messages` with an API key. Defaults to Claude Opus 5.5 (Sonnet 5.5 and Haiku 5.5 selectable). For models that support it, requests opt into Anthropic's server-side refusal fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`): a request a model's safety classifiers wrongly decline is re-run on a recommended other model. A remaining `stop_reason: "refusal"` is shown as "the model declined".
- **OpenAI-compatible**: any `/chat/completions` endpoint. Presets for OpenAI, OpenRouter, Google Gemini, and local Ollama / LM Studio (no key, nothing leaves the PC), or a custom address.

API keys are stored in the OS credential store (Windows Credential Manager, via the `keyring` crate), one per service, never in user.db, so they don't end up in backups. The web side only learns whether a key is saved; requests are made in Rust. Settings has a "Test connection" button.

### Backend: Claude Code CLI (decided 2026-10-20)

Requests run through the **Claude Code CLI** with your existing Claude login, so there's no API key to manage. They count toward your Claude plan's usage limits. Tested command shape:

```
claude -p "<conversation>" --system-prompt "<instructions>" --tools "" --setting-sources ""
       --no-session-persistence --output-format json --model <haiku|sonnet>
```

run from an empty working folder.

- `--tools ""`: the model can only reply with text; it can't read or change files.
- `--setting-sources ""` + empty folder: your personal CLAUDE.md and settings aren't loaded, so they don't steer the output or cost tokens. `--bare` would also do this, but it skips the login, so it fails.
- Each request sends the whole chat so far, so nothing is stored by Claude Code between turns. That keeps the app's AI interface a plain "messages in, text out" call.
- About 5 seconds per reply (measured).
- Opt-in only (since 2026-10-23): the app never runs Claude Code just because it's installed.

### Rules

- **No spending log or cap** (decided 2026-10-20: not useful for personal use on a subscription).
- **One model per helper**, chosen in Settings (Claude Code defaults to Sonnet, the Anthropic API to Opus 5.5).
- **Prompts live in one file**, [`src/ai/prompts.ts`](../src/ai/prompts.ts), so they're easy to read and tune. `LEARNER_PROFILE` there describes you to the AI.
- **Japanese accuracy:** the AI's facts (readings, meanings) come *from our database* in the prompt, not from the AI's memory. The AI is used for creativity and explanation, not as the source of truth.

## Testing approach

- Unit tests for the parts that must be right: scheduling, answer checking (synonyms, kana conversion), unlock order, import script.
- Daily personal use is the real test of everything else.
